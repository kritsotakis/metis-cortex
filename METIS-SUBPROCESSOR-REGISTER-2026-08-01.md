# Metis Cortex — Subprocessor Register

**Prepared:** 1 August 2026
**Status:** Internal operational document. Not yet published on the site — should be linked from the
Privacy Policy once reviewed.

This lists every third party that processes user or matter data on Metis Cortex's behalf, what they
process, and what's actually verified versus still needs confirming. Built by checking the real
production configuration rather than what was originally planned or previously assumed — two real
corrections came out of this exercise, both now fixed on the live site and reflected below:

1. The Privacy Policy originally claimed documents were stored in Cloudflare R2. **Wrong** — no R2
   credentials exist in production and no R2 bucket for this project exists at all (checked via
   `wrangler r2 bucket list`). Documents are on a Fly.io volume.
2. Having corrected #1, this document then claimed the volume was simply "not backed up." **Also
   wrong**, corrected the same day after actually running `flyctl volumes snapshots list` against the
   real volume rather than trusting `fly.toml`'s own comment: Fly's automatic scheduled snapshots
   **are** enabled and real snapshots exist. Not an independent backup — see §1 below for exactly
   what was verified and what still isn't.

---

## 1. Fly.io, Inc.

**What they process:** everything — the application server, the MySQL database (all matter data,
checklist responses, chat history, account emails), and uploaded documents (stored on a Fly-managed
persistent volume, not a separate object-storage service).

**Region:** Sydney, Australia (`syd`) — confirmed directly via `flyctl` for the app, the database
(`metis-cortex-db`), and the storage volume (`metis_data`).

**Encryption:** the storage volume is encrypted at the disk level by Fly (confirmed via `flyctl
volumes list` — `ENCRYPTED: true`) — this is provider-managed disk encryption, not a separate
encryption step Metis applies itself; no application-level document encryption exists in
`server/storage.ts`. Database encryption-at-rest: **to be confirmed** — not independently verified
against Fly's own infrastructure documentation.

**Backup and redundancy — verified directly, not assumed:**
- The volume is hardware-local to a single physical server and machine (confirmed via `flyctl volumes
  list` + `flyctl machines list` — one volume, one attached machine, one zone). It is **not**
  automatically replicated across multiple machines.
- Fly's automatic scheduled snapshots **are enabled**. Confirmed via `flyctl volumes snapshots list`
  against the real production volume on 1 August 2026: 3 snapshots existed, most recent 20 hours old,
  retained for 5 days each — matching Fly's documented default, not a guess.
- **This is not an independent backup.** It's the same provider, the same underlying infrastructure,
  a 5-day retention window, and — as of this writing — **no restore has ever been tested.** No
  recovery point objective (RPO) or recovery time objective (RTO) has been defined.

**The real remediation priority, restated precisely:** production documents currently have one primary
copy on a hardware-local volume, with Fly's own snapshots as the only fallback and no independently
tested restore process. Before real client matters depend on this: implement an independent backup,
test restoring from it, and define an acceptable RPO/RTO. See the incident-response plan.

**Data processing agreement / subprocessor terms with Fly.io:** to be confirmed before production
launch.

## 2. Anthropic (Claude API)

**What they process:** the content of chat messages and the relevant matter/document text needed to
generate a response — for the client-side matter chat, the public marketing-site chat, and (once the
solicitor side is live) case-brief and costs-document drafting.

**Not used for model training:** confirmed — this is Anthropic's own published commercial API term
(data submitted to or generated by the API is not used to train their models under standard
commercial terms). [Anthropic Privacy Center](https://privacy.claude.com/en/articles/8956058-i-have-a-zero-data-retention-agreement-with-anthropic-what-products-does-it-apply-to)

**Retention:** Anthropic's own published default for commercial API traffic is automatic deletion of
inputs/outputs on their backend within a defined retention window (they've published this as being in
the region of 30 days, though the exact current figure should be re-checked against their current
terms rather than relied on from this document). **Metis does not currently have a confirmed Zero Data
Retention (ZDR) agreement with Anthropic** — standard retention terms apply unless/until that's
negotiated. [Claude Platform Docs — API and data retention](https://platform.claude.com/docs/en/manage-claude/api-and-data-retention)

**Region:** Anthropic is a US company; API processing is understood to occur in the US. The specific
data-centre region and whether any regional processing option applies to this account: **to be
confirmed.**

**Data processing agreement:** Anthropic states a Data Processing Agreement is standard with business
accounts — **whether Metis's account has one executed: to be confirmed.**

## 3. Resend (transactional email)

**What they process:** the email address used for magic-link sign-in, and delivery metadata for that
email. Nothing else — Metis does not currently send any other email type (no marketing, no digests).

**Region:** confirmed via Resend's own published documentation — account data, email metadata, and
logs are stored in the United States regardless of which region is used to route/send the email itself.
[Resend Security](https://resend.com/security) · [Resend DPA](https://resend.com/legal/dpa)

**Security posture (as published by Resend, not independently verified by us):** infrastructure
providers audited for SOC 2 Type II and ISO 27001; TLS 1.3+ for data in transit; encryption at rest.

**Data processing agreement:** Resend publishes a standard DPA including Standard Contractual Clauses
for EU data export. Whether Metis has formally executed/relied on it: **to be confirmed.**

---

## 4. Cloudflare (DNS only)

**What they process:** DNS resolution for metiscortex.au. Proxying is deliberately turned off ("DNS
only") for the domain's A/AAAA records, so Cloudflare does not sit in front of application traffic and
does not see request content, matter data, or documents.

**Included here for transparency**, not because it meets the bar of a true data subprocessor — it
resolves a domain name to an IP address and nothing more.

---

## 5. Configured in code but NOT currently active

These integrations exist in the codebase but have no API key configured in production, so they are
currently processing zero data. Listed so this register doesn't go stale silently if either is
switched on later — **whoever configures either of these must update this register at the same time.**

- **Deepgram** (speech-to-text for solicitor-side conference recordings) — no `DEEPGRAM_API_KEY` set.
  Transcription is switched off entirely until this is configured.
- **Google Gemini** — legacy fallback LLM path, no `GEMINI_API_KEY` set. Not in the current request
  path for any live feature.

## What this register does not yet cover

- A formal, signed Data Processing Agreement status for each subprocessor (marked "to be confirmed"
  throughout — this is a real gap, not an oversight in this document).
- Sub-subprocessors of Fly.io, Anthropic, or Resend (i.e., who *they* use) — not requested from any of
  them yet.
- Formal confirmation of Fly.io's own database encryption-at-rest posture.

This document should be re-verified, not just re-read, before it's published or relied on for a real
client's data — the same discipline used to build it (check the actual config, don't restate what was
planned).
